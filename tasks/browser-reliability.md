## 실패 원인과 대책

### 1. 프로바이더 크레딧 부족 (4건) — 2026-09-20 조치

`오류 401: {"type":"error","error":{"type":"CreditsError"...`

폴백 체인(`zai → minimax → openai`)은 401을 폴백 대상으로 보고 있었지만, **쿨다운이 모델 단위였다.** 잔액이 마르면 그 프로바이더의 모든 모델이 똑같이 거부되는데, 모델 하나만 2분 건너뛰고 같은 프로바이더의 다음 모델을 두드렸다. 봇 10개가 전부 `zai`라 영향이 컸다.

조치(`providers/openaiCompat.ts`):

- `isCreditsErr()` — 잔액 오류를 일시적 오류·플랜 문제와 구분
- 잔액 오류는 **엔드포인트 전체**를 1시간 건너뛴다(결제 전까지 풀리지 않으므로)
- 폴백 후보를 고를 때도 잔액이 마른 프로바이더는 통째로 건너뛴다 → `zai` 소진 시 `minimax`로 바로 넘어간다

남은 것: 크레딧 소진을 **미리 감지**해 알릴 수 있는지(프로바이더 API가 잔액을 주는 경우).

### 2. 타임아웃 (2건) — 원인 미특정, 계측이 먼저

`에이전트 오류: The operation timed out.`

이 문구는 `AbortSignal.timeout()`의 기본 메시지라 **어느 지점에서 걸렸는지 알 수 없다.** 후보가 여럿이다.

| 지점 | 한도 |
|---|---|
| `bskExec` (bsk CLI 실행) | 90초 |
| `browser.ts` 화면 분석(비전 모델 호출) | 45초 |
| `browser.ts` 절차 초안 작성 | 60초 |
| `computer.ts` | 120초 |
| 실행 전체 예산 `run_deadline_sec` | 480초 |

조사해 보니 `browser.ts`의 두 지점은 브라우저 조작이 아니라 **그 안의 LLM 호출**이고, 메일 조회 경로와는 거리가 멀다. `bskExec`의 타임아웃은 메시지가 달라(`bsk 실행 시간 초과(90초)`) 이번 실패는 그쪽이 아니다.

**추측으로 한도를 늘리지 않는다.** 잘못 늘리면 실패할 작업에 더 오래 매달릴 뿐이다. 다음 순서는 **실패 기록에 어느 지점·어느 도구였는지 남기는 계측**이고, 그다음 실제 분포를 보고 한도를 조정한다.

- 일시적 타임아웃 재시도는 조회성 명령에만 고려한다. 이미 반쯤 수행된 조작을 다시 하면 안 된다.

### 3. 콘텐츠 정책 거부 (12건) — 2026-09-21 조치

`오류 400: {"contentFilter":[{"level":1,"role":"assistant"}],"error":{"code":"1301","message":"System detected potentially unsafe or sensitive content in input or generation."}}`

폴백 판정이 `isTransientErr`(429·5xx·네트워크·잔액) 또는 `isAuthErr`(401·403)뿐이라 **400은 어느 쪽도 아니어서 그 자리에서 죽었다.** 체인에 `minimax`·`openai`가 있었지만 시도조차 하지 않았다. 봇 10개가 전부 `zai`라 한 번 발동하면 그날 정기 작업이 통째로 실패한다.

조치(`providers/openaiCompat.ts`):

- `isContentFilterErr()` — 콘텐츠 정책 거부를 판정(`contentFilter`·1301·`content policy`·`unsafe or sensitive`)
- `shouldFallback`에 추가 → 다른 프로바이더로 넘어간다. 정책은 프로바이더마다 달라 같은 입력이 다른 곳에서는 통과한다
- **쿨다운은 걸지 않는다**(`ms: 0`). 잔액·플랜 오류와 달리 모델이 못 쓰게 된 게 아니라 *이번 입력*이 거부된 것이라, 건너뛰게 두면 멀쩡한 모델이 다음 요청에서도 빠진다
- 폴백까지 전부 거부되면 `friendlyProviderError`가 JSON 대신 원인·조치를 알려준다

**400 전체를 폴백 대상으로 열지 않았다.** 파라미터 오류 같은 잘못된 요청까지 모든 프로바이더를 헛되이 두드리게 된다. 회귀 테스트로 고정했다(`내용과 무관한 400은 폴백하지 않고 즉시 실패한다`).

**`isInfraFailure()`에는 넣지 않았다.** 폴백이 생긴 뒤로 기록에 남는 콘텐츠 거부는 "체인의 모든 프로바이더가 거부한" 경우이고, 그건 인프라 장애가 아니라 입력 내용 쪽 문제에 가깝다. 이미 쌓인 12건은 폴백이 없던 시절 것이라 절차 실패로 집계되지만, 가장 낮은 browser-skill도 12/15(80%)라 자동 비활성 임계(50%)와는 거리가 있다. 이 판단은 다음 측정에서 다시 본다.

### 4. 대체 경로 — 이미 옮겨져 있다 (2026-09-20 조사 정정)

**앞서 "IMAP으로 옮기는 게 가장 유망하다"고 적었으나 사실과 달랐다.** 조사해 보니 `그룹웨어-메일조회` 스킬은 이미 IMAP을 1순위로 쓰고 있고, 브라우저는 7단계의 **대체 경로**다. IMAP 설정도 `imap.daouoffice.com:993`으로 살아 있고 메일 도구 호출 이력도 있다.

메일 도구 자체도 토큰 측면에서 이미 절제돼 있다 — 목록 기본 30건(최대 100), 미리보기 200자 제한, `preview: false`로 끌 수 있음.

그래서 남은 병목은 **도구가 아니라 LLM 호출**이다. 기록된 실패가 전부 크레딧·타임아웃인 것과 일치한다.

여전히 열려 있는 조사:

- **다우오피스 API** — 메인 현황 조회(결재·게시판 등)는 아직 브라우저 경로다. 공개/사내 API가 있으면 그쪽이 안정적이다.
- 브라우저 경로가 실제로 얼마나 쓰이는지 계측 — IMAP이 1순위라면 브라우저 실패는 드물어야 한다.

## 점검 방법

```sh
# 스킬별 성공률 (인프라 실패 제외한 값이 실제 절차 품질)
sqlite3 "file:$MYBOT/server/data/mybot.db?mode=ro" "
SELECT s.name, COUNT(*) n, SUM(r.ok) ok, SUBSTR(r.fail_reason,1,40)
FROM skill_runs r JOIN skills s ON s.id=r.skill_id
WHERE s.name LIKE '그룹웨어%' OR s.name='browser-skill' GROUP BY s.name, r.ok;"
```

`isInfraFailure()`(`server/src/audit.ts`)가 인프라/절차를 가르는 기준이다. 새로운 인프라 오류 문구가 보이면 이 판정에 추가한다.
