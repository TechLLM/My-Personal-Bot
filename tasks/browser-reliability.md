**성격**: 한 번 끝내는 작업이 아니라 **계속 올려가는 지표**다. 새 실패가 쌓일 때마다 원인을 분류하고, 절차로 고칠 것과 대체 경로로 옮길 것을 나눈다.

**대상**: `그룹웨어-메일조회`, `그룹웨어-메인현황조회`, `browser-skill`

**기록된 실패 6건이 전부 인프라 원인이었다.** 절차가 잘못돼 실패한 건은 0건이다. 그래서 "절차를 고쳐 성공률을 올린다"보다 **인프라 실패를 줄이거나 견디는 쪽**이 먼저다.

## 실패 원인과 대책

### 1. 프로바이더 크레딧 부족 (4건)

`오류 401: {"type":"error","error":{"type":"CreditsError"...`

브라우저 작업은 관찰 결과(DOM·스크린샷)가 커서 토큰 소모가 크다. 잔액이 떨어지면 작업 중간에 끊긴다.

- 스킬 실행 중 401이 났을 때 **폴백 체인이 실제로 작동하는지** 확인한다. 지금은 실패로 기록만 됐다.
- 크레딧 소진을 **미리 감지**해 알릴 수 있는지 본다(프로바이더 API가 잔액을 주는 경우).
- 관찰 결과를 줄인다 — 전체 DOM 대신 필요한 영역만. 스킬 문서의 `Large observations` 절차가 실제로 쓰이는지 확인.

### 2. 타임아웃 (2건)

`에이전트 오류: The operation timed out.`

- `bskExec`의 기본 타임아웃은 90초다. 명령별로 차등할 수 있는지 본다 — `observe`·`screenshot`·`get-html`은 느리고, `click`·`fill`은 빠르다.
- 일시적 타임아웃은 **한 번 재시도**할 가치가 있는지 판단한다. 단, 이미 반쯤 수행된 조작을 다시 하면 안 되므로 조회성 명령만.

### 3. 대체 경로 검토 (더 나은 방법 찾기)

브라우저 자동화는 화면 구조가 바뀌면 깨진다. 같은 일을 더 안정적으로 할 수 있으면 그쪽이 낫다.

- **그룹웨어(다우오피스) API** — 공개/사내 API가 있는지 조사한다. 있으면 메일 조회·현황 조회를 API로 옮기고 브라우저는 백업으로 남긴다.
- **IMAP** — 메일 조회는 이미 `server/src/mail.ts`에 IMAP 경로가 있다. 그룹웨어 메일이 IMAP으로 접근 가능하면 브라우저보다 훨씬 안정적이다. **이게 가장 유망한 후보다.**
- 조사 결과 대체가 가능하면 스킬의 [적용 조건]을 좁혀 브라우저 경로를 후순위로 돌린다.

## 점검 방법

```sh
# 스킬별 성공률 (인프라 실패 제외한 값이 실제 절차 품질)
sqlite3 "file:$MYBOT/server/data/mybot.db?mode=ro" "
SELECT s.name, COUNT(*) n, SUM(r.ok) ok, SUBSTR(r.fail_reason,1,40)
FROM skill_runs r JOIN skills s ON s.id=r.skill_id
WHERE s.name LIKE '그룹웨어%' OR s.name='browser-skill' GROUP BY s.name, r.ok;"
```

`isInfraFailure()`(`server/src/audit.ts`)가 인프라/절차를 가르는 기준이다. 새로운 인프라 오류 문구가 보이면 이 판정에 추가한다.
