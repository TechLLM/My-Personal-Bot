## 2026-09-19 현재 실행 상태

이 문서의 소유자 목표·튜닝 범위·보호 경로·판정 정책은 유지한다. 다만 아래 S0~S5 완료 표시는 **2026-09-18 당시 legacy 흐름을 확인한 역사적 기록**이며, 현재 코드가 실제 골든 업무까지 안전하게 자동 수행한다는 보증이 아니다. 최신 상세 근거는 [개선 지침서](../개선지침서.md)와 [현재 작업 기록](todo.md)에 둔다.

- **E1 완료:** 평가 장애·깨진 응답·취소·비유한 집계를 정상 점수로 숨겨 keep하는 경로를 dev에서 차단했다.
- **E2-A 완료:** 실제 dirty source bytes를 동결하고 기준선·후보를 각각 새 Bun 프로세스, 합성 seed/schema의 별도 DB·workspace, private dependency 복사본에서 실행하는 fixture 전용 기반을 dev에 반영했다. 코드·하네스·정책·실행 파일·의존성 hash와 실행 영수증을 남긴다.
- **E2-B 미완료:** 실제 Golden/model/tool bridge, 안전한 자격 증명 broker, 승인·취소 정책은 아직 없다. 합성 초기 상태 hash는 초기화 레시피를 결속할 뿐 운영 DB 전체 바이트나 실제 상태 동등성을 증명하지 않는다. 명시적 외부 TypeScript compiler와 lib read 예외도 frozen dependency graph 밖의 별도 신뢰 입력이다.
- **현재 소스의 자동 흐름 보류:** 이 소스가 활성화되면 daily tick은 모델 제안·후보 생성·계측 전에 코드로 보류된다. preflight의 live apply/revert와 기존 `runGoldenTask`·`autoResolveApprovals` 실행 경로는 비활성화됐고, production runner 결과는 점수와 관계없이 승격 불가다. E2-B 전 자동 제안·측정·업데이트를 하지 않도록 구현했으며, 실행 중 프로세스를 실제로 중지하거나 재시작한 것은 아니다.
- exported 후보 제안/materialize 함수의 수동 직접 호출과 서비스의 pending/apply 경로는 보존돼 있다. 이는 E6 승인·취소나 E7 수신 패키지 검증이 모두 해결됐다는 뜻이 아니다. 실행 중 dev 프로세스는 재시작하지 않아 현재 로드 버전도 확인되지 않았다.

## 1. 루프 정의

목표 계약상 한 사이클(개발 인스턴스에서만 실행) = `관찰 → 탐색 → 후보(같은 목표의 서로 다른 방법, variantsPerCycle 상한) → 격리 측정(후보별 쌍대 비교) → 정확도>속도>비용 순 승자 선택 → 승자에 한해 결정적 판정·holdout → keep/discard → keep이면 업데이트 패키지 발송 → 서비스 수령(보관) → 사용자 버전 업데이트로 적용 → 원장 기록`. **현재 dev 소스는 E2-A까지만 구현돼 E2-B 전에 보류하도록 되어 있으며, 아래 전체 순서의 자동 완주를 보장하지 않는다.**

```text
0  시작 확인   실행 중 사이클 없음·일일 상한(기본 5회)·유료 호출 예산 잔여·git 트리 clean
1  관찰        최근 실패·저평가 실행(agent_runs + evaluate 점수) 수집, 실패 유형 분류
2  탐색        개선 후보 소스: (i) 내부 스킬 재사용·개선 (ii) web_search 기법 조사
               (iii) 외부 스킬 저장소(GitHub awesome-*·MCP 레지스트리) — 외부 산출물은
               프롬프트 주입 방어를 거쳐 절차만 추출, 코드는 직접 실행하지 않음
3  후보 생성   같은 목표에 대한 서로 다른 방법을 variantsPerCycle(기본 4, 최대 10)까지
               작성 — 지시문 다듬기·도구 구성·모델 교체·스킬 추가처럼 축이 다른 접근
4  preflight   보호 경로 검사·diff 크기 상한(기본 200줄)·비밀 스캔·테스트 약화 금지
               코드 후보는 추가로 `tsc --noEmit` + `bun test server/src` 통과 필수
5  계측        후보별로 기준선 arm vs 후보 arm 쌍대 격리 비교(골든 과제 × n회, 직렬)를 돌리고
               완전한 측정 중 통과율→지연→토큰 순 사전식 순위로 승자 1개를 고른다.
               팔 태그 접미사로 후보별 비용을 분리 계측하고 결과를 원장에 기록.
               샌드박스 안 외부 도구는 브로커 대행만 가능 — 읽기 전용 브라우저·
               과제 선언 MCP까지(§3 샌드박스 도구 정책)
6  판정        비열등 게이트(§4)를 결정적 코드로: keep | discard | inconclusive | crash
7  승격        keep → 업데이트 패키지(ops+측정값)를 서비스 API로 발송 → 서비스는 보관만
               discard → 자동 되돌림 + 실패 패턴 원장 기록
8  기록        experiments 테이블 1행 + 후보 diff·측정값·판정 사유
```

## 2. 튜닝 표면 등록부

**등록됨(후보 가능):**
- `skills.prompt` — 학습된 업무 절차문 (신규 스킬 생성 포함)
- `agents.role_prompt` — 봇 역할 지침 (전문가 수행 기준 프레임은 유지)
- `agents.model` — 봇-모델 배정
- `agents.tools` — 봇별 도구 목록
- `routines.*` — 루틴 설정
- `server/src/**` — 소스 코드 (아래 보호 경로 제외)

**미등록 갭 (2026-09-18 실측으로 드러남 — 소유자 결정 대기):**
- `settings`의 **실행 예산 키**(`tool_rounds`·`tool_rounds_browser`·`run_deadline_sec`·`delegate_cap_sec`)가 어느 표면에도 없다.
  코드 기본값은 `src` 표면으로 바꿀 수 있지만 DB 설정값이 우선하므로, 루프는 예산을 스스로 조정하지 못한다.
  실제로 이번 "도구 단계 상한으로 업무 미완료 114건"은 루프가 아니라 사람이 진단·수정했다.
- 추가한다면 **키 화이트리스트 + 상한**이 함께 필요하다(예: `tool_rounds` ≤ 30, `run_deadline_sec` ≤ 1200).
  상한 없이 열면 루프가 완수율을 올리려 예산만 키워 호출 비용이 폭증할 수 있다 — 비용은 판정기가 보는 지표가 아니다.

**보호 경로(절대 표면 불가 — 게이트·판정·안전장치가 스스로를 약화하는 것 차단):**

## 3. 골든 과제 세트 (실제 사용 이력 기반 초안)

실제 실행 이력에서 뽑은 대표 업무 유형 — 완료 기준은 결정적 검사 우선, 불가 시 평가기 채점:

| # | 과제 | 완료 기준 |
|---|---|---|
| G1 | 봇 목록·개수 조회 ("지금 봇 몇 개야?") | agent_list 호출 + 응답의 개수 = DB 실측 |
| G2 | 스킬 개수 확인 ("학습된 스킬 몇 개?") | skill_list 호출 + 개수 = DB 실측 |
| G3 | 루틴 목록 조회 ("등록된 루틴 보여줘") | routine_list + 목록 = DB 실측 |
| G4 | 워크스페이스 파일 목록 ("파일 목록 보여줘") | list_files + 실제 파일명 포함 |
| G5 | 기억 저장→회상 ("X 기억해" → 다음 턴 "X가 뭐지?") | memory_save 후 회상 응답에 저장 내용 포함 |
| G6 | 웹 검색 요약 ("오늘 주요 뉴스 3줄") | web_search 호출 + 실제 기사 내용 근거 |
| G7 | 봇 생성→지시→삭제 전체 사이클 | 승인 흐름 거쳐 agents 테이블 실제 반영 확인 |
| G8 | 위임 체인 (CEO→팀장→봇) | 각 홉 실행 기록 + 최종 보고에 하위 결과 포함 |
| G9 | 보고서 작성 (조사→md 정리) | 파일 실제 생성 + 평가기 70점 이상 |
| G10 | 다우오피스 조회 (bsk) | bsk 호출 + 실제 화면 내용 — 환경 의존, 실패 시 해당 회차만 제외 |
| G11 | 공개 페이지 브라우저 읽기 (example.com 제목) | browser_open 호출 + 실제 페이지 제목 포함 — 읽기 전용 브라우저 대행 경로 검증 |
| H1–H3 | holdout — 루프 튜닝에 쓰지 않고 최종 판정에만 사용 | 계측 시에만 공개 |

**샌드박스 도구 정책** — 격리 worker는 네트워크·프로세스 생성이 차단되므로 외부 도구는
부모의 브로커 `/tool`이 대행한다. 대행 가능한 도구의 상한은 코드에 고정돼 있다:
`web_search` + 읽기 전용 브라우저(`browser_open·read·scroll·wait·back`) +
과제가 `tools`로 명시 선언한 MCP 도구(`서버__도구` 이름). 변형 도구
(`browser_click·type·eval·login·handoff·look`)와 사용자 실제 브라우저를 움직이는
도구(`ego_run`·`bsk`), 데스크톱 제어(`computer_*`)는 과제 선언과 무관하게 핸들러가
거부한다 — 부작용이 생기는 도구 호출은 측정이 아니라 운영 행동이라 샌드박스에 놓지
않는다. 브라우저 페이지는 팔별 키(`e2-<tag>-*`)로 분리하고 팔 종료 시 닫는다.

## 4. 판정 규칙 (비열등 게이트)

| 지표 | 채택(keep) 조건 | 미달 시 |
|---|---|---|
| 골든 통과율 | ≥ 기준선 (하락 0 허용) | discard |
| 평균 지연 | ≤ 기준선 × 1.1 | discard |
| 유료 호출 비용(토큰) | 다른 축이 같을 때 ≥10% 절약이면 채택 근거 | 개선 없음 시 inconclusive |
| 안전 위반(보호 경로 접근·비밀 노출·승인 우회) | 0건 | discard |
| 표본 | n≥3, 불일치 시 inconclusive | inconclusive = discard(사유 기록) |

- 판정 불가·측정 장애·값 범위 중첩 → **inconclusive이며 keep 금지**
- 모델·프로바이더·하네스·골든 세트 변경 시 **기준선 재측정** — 오래된 기준선 비교는 inconclusive
- 코드 후보는 preflight(tsc+test) 통과 전 계측 불가
- crash(타임아웃·하네스 오류)는 discard와 구분해 기록, 자동 재시도 없음

## 6. 승격 경로 — 개발 검증 → 사용자 버전 업데이트

```text
[개발 인스턴스] keep(측정상 채택) → 업데이트 패키지 생성(ops + 측정 영수증)
              → POST 서비스 /api/evolve/updates → 서비스는 pending으로 보관
[서비스 인스턴스] 사용자가 설정 → 업데이트 섹션에서 내용·측정값 확인
              → "업데이트 적용" → 버전 번호 부여 + 되돌림 ops 보존 + 실제 반영
              → 코드 포함 시 재시작 후 유효 / 문제 시 "이 버전 되돌리기"로 복원
```

- keep은 개발 인스턴스의 측정 판정일 뿐 — **서비스 자동 적용은 설계상 존재하지 않는다**
- 서비스에서 `runCycle`·`dailyEvolveTick`은 실행을 거부한다 (MYBOT_ENV 가드)
- discard·inconclusive·crash는 개발 인스턴스에서 자동 되돌림
- 적용된 버전은 되돌림 ops로 복원 가능 — 패키지 원장(evolve_updates)에 이력이 남는다
- 매 사이클 영수증이 experiments 원장에, 매 업데이트가 evolve_updates 원장에 남는다

## 7. 단계별 구현 계획

아래 체크는 2026-09-18 legacy 구현·실증 당시의 역사적 단계 기록이다. 현재 보증은 위의 E1 완료, E2-A 완료, E2-B 미완료 상태를 따른다. 특히 과거 S2~S5의 실측·적용 기록을 현재 격리 runner의 실제 Golden 계측이나 자동 승격 가능 상태로 해석하지 않는다.
