# 1단계: 접속 경로를 유지하는 접근 통제

목표: Mac mini의 `http://localhost:5274/`와 `https://bot.myxcloud.co.kr/`를 유지하면서 미인증 API 접근을 막는다. 맥의 LAN 주소는 192.168.237.74다. LAN IP의 5274 포트를 직접 공개하는 것은 이번 요구에 포함하지 않는다.

최초 작업에서는 `codex/mybot-access-stage1` 브랜치를 준비하고 개발 공간 `MyBot-dev`에 소스만 적용했다. 이후 다른 작업에서 서비스 접근 통제와 관리자 릴리스 경로가 반영됐다. 현재 서비스의 미인증 `/api/access`는 401, 인증된 `/api/release`는 200이며 dev `/api/access`는 암호 미설정으로 503이다. 이번 재점검에서는 문서만 갱신하고 서비스·코드를 변경하지 않았다. 상세 현재 상태는 [dev 개선 지침서](../개선지침서.md)를 참조한다.

## 확인한 연결

- Nginx 설정: `/opt/homebrew/etc/nginx/servers/bot.myxcloud.co.kr.conf`.
- HTTP 도메인은 HTTPS로 리다이렉트하며, HTTPS는 `http://127.0.0.1:5274`로 전달한다.
- 원래 Host를 유지하므로 앱은 도메인 Host와 HTTPS Origin을 허용해야 한다. 임의의 X-Forwarded-* 헤더를 신뢰해 Origin을 확장하지 않는다.
- localhost health와 `curl --resolve`를 통한 로컬 Nginx HTTPS 경로는 200 응답을 확인했다. 공인 도메인 주소로 직접 연결한 요청은 이 실행 환경에서 시간 초과였다. 외부 기기에서의 접속 성공을 검증한 것은 아니다.

## 변경

- 앱의 기본 수신 주소: 127.0.0.1. 도메인은 기존 Nginx를 통해 접속한다. Nginx 설정 자체는 변경하지 않는다.
- 공개 health 외 API는 암호가 없으면 503, 암호가 틀리거나 없으면 401이다.
- 허용 Origin은 인스턴스 포트의 localhost·127.0.0.1과 기본 HTTPS 도메인이다. 추가 주소는 `MYBOT_ALLOWED_ORIGINS`로 명시한다.
- 접속 암호 해석 순서: `MYBOT_ACCESS_CODE` → 실행 사용자 소유·권한 0600인 `server/data/access.key` → 기존 DB `access_code`. DB fallback은 파일이 실제로 없을 때만 사용하며 값이 없으면 잠긴다. 링크·잘못된 권한·빈 환경변수로 fallback을 우회하지 않는다. 재점검 시 서비스 DB 암호는 설정됨, dev DB 암호는 비어 있음으로 확인했다. 비밀값은 기록하지 않는다.
- 로그인 전에 봇·설정·폴링을 시작하지 않는다. 승인 후 브라우저 localStorage에 접속 암호를 보관한다. localhost와 도메인은 별도 브라우저 저장소이므로 각각 처음 한 번 입력해야 한다.
- 실시간 이벤트·브라우저 화면·이미지는 인증 헤더를 사용한다. URL에는 암호를 넣지 않는다.
- 키 파일을 만드는 `bun scripts/provision-access.ts`는 앱·DB를 불러오지 않고 새 암호만 소유자 전용 파일에 저장한다. 기존 키는 덮어쓰지 않고 비밀값은 출력하지 않는다.

## 검증

- 접근 통제·프런트 실시간 연결 테스트 9개 통과.
- 서버·웹 TypeScript 검사 및 `git diff --check` 통과.
- 격리 작업트리에서 웹 production 빌드 완료. 네트워크와 작업트리 밖 쓰기를 차단한 sandbox에서 기존 의존성으로 빌드했다. 설치하지 않았다.
- 위 9개 테스트·타입 검사·빌드는 최초 작업의 결과이며 이번에는 재실행하지 않았다. 이번에는 읽기 전용 DB·소스 확인과 인증 GET 응답을 확인했다. 실제 로그인 UI·외부 기기·배포 후 복구 인수 검증은 별도다.

## 적용·복구 게이트

### 확정 운영 방향 (2026-09-19)

개발·검증은 dev에서 진행하고, 서비스는 검증된 릴리스를 수령해 사용자 확인 후 업그레이드한다. 서비스 공간에서 직접 개발하거나 dev 변경 전체를 곧바로 덮어쓰지 않는다. 전체 단계의 진행 현황은 [dev 개선 지침서](../개선지침서.md)를 참조한다.

최초 1단계 후보는 `4e355f2dd0a9af7cba5fd477b54c4a228edf1609`이며 서비스에는 그 뒤의 변경도 들어갔다. 새 `release.ts`는 사람이 검토한 앱 전체 릴리스 통로로, 로컬 release 브랜치를 서비스 관리자가 적용하는 방식이다. 기존 `evolve.ts`는 봇의 표면 변경 통로로 보호 경로를 유지한다. 전체 릴리스 통로를 중복 구현하지 않고, dev 기준 정합성과 검증 영수증·승인 SHA·복구 검증을 보강한다. 두 통로의 차이와 미완료 사항은 개선 지침서에 기록했다.

코드 적용, 키 생성, 웹 빌드 교체, 프로세스 재시작을 구분한다. 운영 적용 전 현재 실행·대기 승인·예약 상태와 실제 외부 효과를 점검하고, 정확한 코드 버전과 DB·설정·기존 웹 빌드를 보존한다. 암호 파일은 대화나 로그에 출력하지 않는다.

서비스 적용·재시작은 검증된 릴리스의 업그레이드 절차 안에서 별도 확인 후 진행한다. 암호 설정 완료 후 미인증 API의 401과 인증 API의 200, localhost와 로컬 Nginx 경로, 실시간 연결을 검증한다. 외부 기기 도메인 접속도 사용자 확인이 필요하다. 실패 시 기존 코드·웹 빌드로 복구하되, 서버 시작 과정에서 생성된 업무를 무조건 재실행하거나 DB만 과거로 되돌리지 않는다.

2단계 개발 격리로 자동 진행하지 않는다.
