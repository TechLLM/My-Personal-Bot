# 릴리스 통로 보강 — R2 기동 실패 차단

**날짜**: 2026-09-19
**범위**: `server/src/release.ts`, `server/src/release.test.ts`
**근거 문서**: 개선지침서 "다음 작업" 4번, 완료 기준 R2

## 배경 — 무엇이 구멍이었나

첫 릴리스 통로는 테스트·타입검사·웹 빌드를 통과하면 곧바로 `process.exit(0)`으로 재시작했다. 여기에 빈 곳이 있었다.

세 검사를 모두 통과해도 **서버가 기동 자체에 실패할 수 있다.** import 오류, 라우트 배선 실수, 미들웨어 초기화 실패는 테스트가 잡지 못하는 경우가 있다. 그 상태로 재시작하면 launchd(`KeepAlive=true`)가 계속 다시 띄우려 하고 **크래시 루프**에 빠진다. 그 시점에는 화면도 죽어 있어 되돌리기 버튼조차 누를 수 없다. 복구 수단이 화면 안에만 있었던 것이 문제였다.

## 변경

- 검증 단계를 `Gate[]`로 구조화하고 `runGates`를 분리했다. 앞 단계가 실패하면 뒤 단계를 돌리지 않는다.
- **기동 시험** 단계를 마지막에 추가했다. 새 코드를 임시 포트에서 실제로 띄워 `/api/health`가 응답하는지 확인하고 종료한다. `NODE_ENV=test`로 띄우므로 메모리 DB를 쓰고 운영 DB·외부 채널은 건드리지 않는다.
- 기동 시험은 웹 빌드 **뒤**에 둔다. 순서가 바뀌면 빌드 전 상태를 검증하게 되어 실제 배포본과 달라진다. 이 순서를 테스트로 고정했다.

## 검증한 것

서버 전체 **89개 통과·0개 실패**, 서버 타입검사 0건.

릴리스 관련 11개 중 이번에 추가한 것:

- 모든 단계 통과 시 순서대로 실행된다
- 한 단계가 실패하면 **거기서 멈추고 뒤 단계를 돌리지 않는다**(실행 로그로 확인)
- 마지막 단계의 실패도 놓치지 않는다
- 기동 시험이 웹 빌드 뒤 마지막에 온다
- **기동 시험이 뜨지 못하는 코드를 잡아낸다** — 임시 디렉터리에 즉시 throw하는 `index.ts`를 만들어 실패를 주입하고 `ok:false`를 확인

`bootCheck`를 현재 코드로 직접 실행해 `ok:true`(256ms)도 확인했다.

## 검증하지 않은 것

- **롤백의 `git reset --hard` + 웹 재빌드가 실제로 실행되는 경로.** 게이트가 실패를 돌려주면 롤백이 호출되는 구조는 확인했지만, 실제 저장소에서 되돌아가는 것까지 실행하지는 않았다. 서비스나 dev에서 일부러 실패를 내는 것은 위험하고, 격리 저장소를 따로 세우는 작업은 이번 범위 밖이다. 다음 릴리스가 실패하면 그때 실측된다.
- 재시작 후 새 프로세스의 health. 기동 시험이 사전에 같은 것을 확인하므로 사후 확인은 두지 않았다.

## 남은 작업

- **R1** — 승인 SHA와 검증 영수증. 어떤 커밋을 누가 언제 승인했고 어떤 검사를 통과했는지 남긴다.
- **R3** — 적용 전 저널. 재시작 실패로 프로세스가 돌아오지 못한 경우를 다음 기동에서 발견할 수 있게 한다.
- **E2-B / E3** — 자기개선 격리 worker의 실모델 연결과 동일 조건 비교. 성격이 다른 작업이며 개선지침서를 따른다.
